# M8 额度账本样例事件

`quota_events.json` 故意把到达顺序打乱，覆盖本模块的全部关键判定（时间均为 UTC，
展示层按 +08:00）：

| 场景 | 事件 | 预期结论 |
|---|---|---|
| 回执先于首发到达 | `R-001`（received 最早，受理 11-02）排在首发 v1 前面 | 进收件箱后仍按业务时间钉版 v1，不按到达顺序覆盖事实 |
| 更正晚到、旧受理不重算 | v2 更正 1000 → 800（11-06 发布） | R-001/R-002 共 900 钉在 v1；v1 视角缺口 0；v2 当前视角可用 650（800−150），新申报看更正后余额 |
| 切换失败保留上一完整版本 | v3 发布时间 11-04 早于 v2 的 11-06（时间倒挂） | v3 落 rejected（`F_VERSION_INVERSION`），当前指针仍指 v2 |
| 受理即超占 | 绿池 G-001 申请 2100，总额 2000 | 受理事实保留、记超额缺口 100，可用余额截到 0 |
| 撤销池不再受理 | 绿池 v2 撤销 | 池状态 VOIDED；撤销后到达的新回执按 `F_RECEIPT_VOID_POOL` 隔离 |
| 挂起不丢失 | `R-004-EARLY` 受理时间 09-01 早于首发 10-20 | 保持 pending（`F_RECEIPT_PENDING`）；补齐 09-01 之前的首发版本后，续跑自动匹配钉版 |
| 幂等重跑 | 同一批事件再 POST 一次 | 摘要命中，`F_DUP_EVENT` 跳过，不新增运行流水、占用与回执行数不变 |
| 中断续跑 | 测试用 `hooks.fail_on_digest` | 已确认更正/受理已落库；`/api/quota/resume` 只处理剩余 pending，终态与一次跑完全一致 |

一步导入（容器内）：

```bash
curl -sS -X POST http://localhost:18200/api/quota/process \
  -H 'content-type: application/json' \
  --data-binary @sample_data/quota_events.json
open http://localhost:18200/quota
```

## 核算口径（POOL-2026-TECH）

- v1（总额 1000）：钉版回执 R-001 600 + R-002 300 = 占用 900 → v1 视角可用 100、缺口 0；
  这些受理**不随 v2 更正重算**。
- v2（总额 800，当前）：钉版回执 R-003 150 → 当前占用 150、**可用 650**、缺口 0。
- 全池占用 = 900 + 150 = 1050，与回执账 CSV 逐项求和一致。
- `R-004-EARLY` 因受理时间早于池内任何版本，保持挂起，不占用任何版本。
